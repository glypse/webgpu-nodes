# Performance baselines

The numbers the Rust port has to beat (task 8 of `rust-port-prep.md`). Recorded 2026-11-26.

## What is measured

Two projects: the demo scene (`fixtures/perf/demo.json`, a copy of `packages/core/src/scenes/default.json`) and a large synthetic project (`fixtures/perf/large.json`, generated by `packages/core/scripts/perf.ts`, deterministic). The large one has about 3,500 nodes and 3,500 links across 22 documents: one linear chain of 200 math steps, 40 short chains of 15 steps that each end in an instance of a user group, 20 short chains of 10 steps, 10 repeat zones with state items, three render textures (one feeding a copy of the demo's Glow group, which holds a Repeat Passes loop), three standard-library group instances, and a fan-in tree of add nodes into the output. The 20 user groups hold about 75 nodes each; groups 10 to 14 hold a group that holds another, so the deepest instance sits three groups in.

CPU rows, all from `packages/core/scripts/perf.ts`, timed in ms over 30 runs after 3 warm-up runs:

- **Load**: `new GraphModel(project)`.
- **Codegen**: `generateRenderPlan` on a warm model.
- **Shader hash**: `reachableShaderHash` on a warm model, the first step of the editor's per-edit check.
- **Value edit, connect, move**: the edit (`apply`) followed by what the editor recomputes (`Editor.svelte` and `graph-view.svelte.ts`): the active document's zone and frame analyses and unavailable links, then the shader hash, regenerating the plan only when it changed with the uniform inputs ignored. A value edit changes only a uniform, so it skips codegen; a connection changes the shader, so it regenerates; a move changes no shader input. Connect is undone outside the timing.
- **Cold**: each analysis on a freshly loaded model, timed on its first call (`frameValueAnalysis` with the pass analysis already computed). `passAnalysis` is timed through `renders()`, since its links are computed lazily per edge.

GPU rows are the frame time of `fixtures/gpu/perf-demo` and `fixtures/gpu/perf-large`: the project drawn at 1920 by 1080, `frameTime` averaging 40 frames, best of three rounds (`packages/runtime/src/gpu-tests/harness.ts`).

## How to rerun

- CPU, from `packages/core`: `bun run perf` prints the table; `bun run perf --write` also writes it into this file. `bun run perf --write-large` regenerates `fixtures/perf/large.json` and `fixtures/gpu/perf-large/project.json` first (the demo copies are plain copies of `default.json`).
- GPU: with the dev server running at http://localhost:5173, open http://localhost:5173/gpu-tests?only=perf in a browser at 1920 by 1200 and read the `ms a frame` of each fixture.

Bun runs the CPU numbers on JavaScriptCore; the editor runs the same code on V8 in the browser, so those differ. The Rust/WASM comparison has to be measured the same way: the same project, the same operations, in the same runtime.

## Machine

- CPU and GPU: Apple M2 (integrated GPU), 16 GB memory.
- macOS 27.2.1, Bun 1.4.5.
- Browser: the built-in browser pane of the Claude desktop app, WebGPU.

## GPU results

| Fixture      |                                         Frame time, ms |
| ------------ | -----------------------------------------------------: |
| `perf-demo`  |             7.9 median; 6.8 to 9.8 over six page loads |
| `perf-large` | about 2.0; 1.7 to 2.0 over four page loads that passed |

`perf-large` overflowed the browser's call stack in some loads (`Maximum call stack size exceeded`), and the same project ran fine under Bun. The likely cause is the depth of the longest chain of links, which codegen recurses along, and the browser's stack is smaller than Bun's. The first version had a 600-step chain with group instances and failed on its first load. A second version, with group instances in the long chain, passed once and failed once. The version here keeps the long chain linear, with 200 steps and no groups, and passed every load since. The recursing function was not identified; this is the limit the Rust port should remove.
